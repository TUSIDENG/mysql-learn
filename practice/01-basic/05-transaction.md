| 场景 | 观察点 | 预期 |
| --- | --- | --- |
| 1a RC | A 两次读同一行，B 在期间提交修改 | 1000 → 5000（不可重复读） |
| 1b RR | B 在 A 事务期间提交，A 再读 | 5000 → 5000（可重复读） |
| 2 FOR UPDATE | B 请求 A 持有的锁 | 被阻塞，A 提交后返回 |
| 3 锁超时 | A 持锁 5s，B 超时设 3s | B 报 **ERROR 1205** |
| 4 无索引 | A 按 status=0 更新，B 改 status=1 的行 | B 仍被阻塞 |
| 5 有索引 | 加 `idx_status` 后 B 改不匹配行 | B 立即成功 |
| 6 间隙锁 | A 锁 `sku_id>2`，B 插入新行 | B 被阻塞至 A 提交 |
| 7 死锁 | A/B 反向交叉更新 | 一方报 **ERROR 1213** 并整个回滚 |

## 一、先分清两个错误：1205 与 1213

很多人把"锁超时"和"死锁"混为一谈，它们是**两套完全不同的机制**：

| 对比项 | 锁超时 Lock Wait Timeout | 死锁 Deadlock |
| --- | --- | --- |
| 错误码 | **1205**，SQLSTATE `HY000` | **1213**，SQLSTATE `40001` |
| 报错文案 | Lock wait timeout exceeded; try restarting transaction | Deadlock found when trying to get lock; try restarting transaction |
| 本质 | **单向等待**：我等的锁一直没人释放，等够了时间 | **循环等待**：我等你、你等我，形成等待环 |
| 处理方式 | 被动超时：由计时器触发 | 主动检测：`innodb_deadlock_detect` 发现环立即打断 |
| 默认触发时间 | `innodb_lock_wait_timeout` = **50 秒** | 通常毫秒级，立即触发 |
| 回滚范围 | **只回滚当前这一条 SQL**，事务还在 | **回滚整个事务** |
| 应用应该怎么做 | 审视持锁方为什么慢；自行决定重试语句还是回滚 | 立即**重试整个事务**（40001 语义就是"可重试错误"） |

一句话记忆：

- **1205 = 等不到（对方太慢/不提交）**
- **1213 = 互相等（加锁顺序打架）**

## 二、InnoDB 锁的分类

理解死锁前，先建立锁的全景图。

### 2.1 按模式（兼容性）分

| 锁 | 名称 | 兼容性 |
| --- | --- | --- |
| **S** | 共享锁 / 读锁 | S 与 S 兼容；S 与 X 互斥 |
| **X** | 排他锁 / 写锁 | X 与 S、X 都互斥 |

- 普通 `SELECT` 是**快照读**，走 MVCC，读历史版本，**不加锁**。
- `INSERT / UPDATE / DELETE` 自动加 **X 锁**。

### 2.2 按粒度分

| 锁 | 说明 |
| --- | --- |
| Record Lock（记录锁） | 锁**单条索引记录** |
| Gap Lock（间隙锁） | 锁索引记录之间的**空隙**（防止别的事务插入），间隙锁之间**互不阻塞** |
| Next-Key Lock | Record Lock + 前面的 Gap Lock，是 RR 下默认的加锁单位 |
| 插入意向锁 | INSERT 前在间隙中加的一种特殊间隙锁，多个插入不同位置本不冲突，但会被间隙锁挡住 |
| 意向锁 IS/IX | 表级锁，加行锁前自动加，用于快速判断"能否给表加表锁" |
| AUTO-INC 锁 | 自增列分配时的表级锁（可用 `innodb_autoinc_lock_mode` 调为更轻的模式） |
| MDL（元数据锁） | 访问表即持有 MDL 读锁；DDL 需 MDL 写锁 |

### 2.3 快照读 vs 当前读

| 类型 | 语句 | 是否加锁 |
| --- | --- | --- |
| 快照读 | 普通 `SELECT` | 不加锁，读 MVCC 快照 |
| 当前读 | `SELECT ... FOR UPDATE`（X） | 加锁，读最新版本 |
| 当前读 | `SELECT ... FOR SHARE`（S，8.0+） | 加锁，读最新版本 |
| 当前读 | `SELECT ... LOCK IN SHARE MODE`（S，旧语法） | 加锁 |
| 当前读 | `INSERT / UPDATE / DELETE` | 自动加 X 锁 |

### 2.4 关键认知：行锁是加在索引上的

这是 MySQL 锁最重要、也最容易踩坑的一点：

> InnoDB 的行锁不是锁"数据行"，而是锁"**索引记录**"。

- 语句走了索引 → 只锁匹配的索引记录。
- 语句**没走索引** → InnoDB 只能逐行扫描，**给扫过的每一行都加上锁**，相当于大范围锁定，极端时近似锁表。
- 即使表上有索引，优化器若认为全表扫描更快（如低选择性列、数据量小），照样锁很多行。

## 三、锁等待与锁超时（1205）

### 3.1 如何产生

形成条件很简单：

```text
事务 A 持有某行的 X 锁，且迟迟不 COMMIT / ROLLBACK
事务 B 也要修改同一行（申请 X 锁）→ 与 A 的锁不兼容 → B 进入等待队列
B 等待时间超过 innodb_lock_wait_timeout（默认 50s）
→ ERROR 1205 (HY000): Lock wait timeout exceeded
```

常见根因：

1. **持锁事务本身很慢**：一条更新关联了多张大表、扫了很多行，事务执行时间长。
2. **事务里夹杂了慢操作**：事务中调用外部接口、写文件、人工审批、`sleep` 等，锁一直被攥在手里。
3. **长事务 / 忘记提交**：代码异常未提交、交互式客户端开了事务忘记 `COMMIT`。
4. **热点行**：所有并发都更新同一行（如秒杀库存、全局计数器、账户总行）。
5. **没走索引导致锁范围过大**：一个看似普通的更新无意中锁住了大量行。
6. **锁等待链**：C 等 B、B 等 A，A 一慢，后面全部超时。
7. **MDL 等待**：长事务未提交时执行 DDL，DDL 等 MDL 写锁，并阻塞之后所有访问该表的语句。

### 3.2 超时发生时回滚了什么

这是非常关键的细节：

- **1205 只回滚"触发超时的那一条语句"，整个事务仍然存在，之前语句的修改都还在、锁也还持有。**
- 因此应用层不能拿到 1205 就当无事发生，必须显式决定：继续重试这条语句，还是 `ROLLBACK` 整个事务。
- 相比之下，1213 死锁是**整个事务被回滚**。

### 3.3 相关参数

```sql
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';  -- 行锁等待，默认 50 秒
SET SESSION innodb_lock_wait_timeout = 5;        -- 当前会话调小（演练/应急）
SET GLOBAL  innodb_lock_wait_timeout = 10;       -- 全局，新连接生效

SHOW VARIABLES LIKE 'lock_wait_timeout';         -- MDL/表级锁等待，默认 31536000 秒(1年)!
SET SESSION lock_wait_timeout = 10;              -- 让 DDL 拿不到 MDL 时快速失败
```

> 生产建议：`innodb_lock_wait_timeout` 常从默认 50s 下调到 **5~10s**，让问题更快暴露、连接更快释放；具体值要结合业务事务正常耗时评估。

## 四、死锁（1213）

### 4.1 如何产生

两个或更多事务，**互相持有对方想要的锁，又互相等待对方释放**，形成闭环：

```text
事务 A：持有行1的锁，想申请行2的锁（行2 被 B 锁着）
事务 B：持有行2的锁，想申请行1的锁（行1 被 A 锁着）
        A 等 B，B 等 A → 谁也推进不了 → 死锁
```

用操作系统的经典理论，死锁需要同时满足四个必要条件，InnoDB 场景对应如下：

| 必要条件 | InnoDB 中的含义 |
| --- | --- |
| 互斥 | X 锁同一时刻只能被一个事务持有 |
| 持有并等待 | 拿着已有锁的同时去申请新锁 |
| 不可剥夺 | 锁不能被别人强行抢走，只能等持有者主动释放 |
| 循环等待 | 事务间形成等待环（这是唯一可由"加锁顺序"打破的条件） |

### 4.2 InnoDB 如何处理死锁

InnoDB **不会傻等**，它有主动机制：

1. **死锁检测**（`innodb_deadlock_detect=ON`，默认开启）：每当一个事务因加锁进入等待，InnoDB 检查是否出现等待环，一旦发现，**立即**挑选一个"代价最小"（通常是修改行数少、权重低）的事务作为牺牲者，将其**整个回滚**并返回：

   ```text
   ERROR 1213 (40001): Deadlock found when trying to get lock;
   try restarting transaction
   ```

2. **关闭检测的兜底场景**：在极端高并发的热点行场景，死锁检测需要遍历等待事务，复杂度接近 O(n²)，本身可能吃掉大量 CPU。此时少数业务会选择：

   ```sql
   SET GLOBAL innodb_deadlock_detect = OFF;
   ```

   关闭后只能依赖 `innodb_lock_wait_timeout` 在 50s（或更短）后打破等待，代价是请求要等更久，**必须配合完善的应用重试**，一般不建议新手关闭。

3. **40001 是"可重试错误"**：SQLSTATE `40001` 的标准语义就是"事务回滚，请重试"。应用捕获 1213 后，正确做法是**重新执行整个事务**。

### 4.3 死锁日志长什么样

`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段会给出两个事务各自：

- 正在执行的 SQL；
- 已经持有的锁（HOLDS THE LOCK）；
- 正在等待的锁（WAITING FOR THIS LOCK TO BE GRANTED）；
- 最终谁被回滚（WE ROLL BACK TRANSACTION）。

8.0+ 还可以让所有死锁进入错误日志，便于事后排查：

```sql
SET GLOBAL innodb_print_all_deadlocks = ON;
```

## 五、典型死锁场景剖析

### 场景 1：交叉更新（最经典）

| 时序 | 会话 A | 会话 B |
| --- | --- | --- |
| t1 | `UPDATE ... WHERE id=1`（拿到 id=1 的 X 锁） | |
| t2 | | `UPDATE ... WHERE id=2`（拿到 id=2 的 X 锁） |
| t3 | `UPDATE ... WHERE id=2`（等待 B） | |
| t4 | | `UPDATE ... WHERE id=1`（等待 A）→ 检测到环 |

**根因：两个事务加锁顺序相反。**

### 场景 2：唯一索引并发插入（间隙锁死锁）

多个事务同时插入相同唯一键值附近的数据时：

1. 事务 A、B 插入冲突，先都在同一间隙持有 **S 锁/插入意向等待**；
2. 间隙锁之间不互斥，于是多个事务可以同时停在同一个间隙；
3. 它们随后又都想把锁升级成 **X 锁**完成真正插入；
4. 你等我的 S 锁、我等你的 S 锁 → 死锁。

这是"批量导入 / 重复提交 / 唯一索引 + 高并发插入"下非常高发的死锁。

### 场景 3：无索引更新导致锁范围重叠

不同事务按不同的非索引列条件更新，本以为各改各的，实际上因为走全表扫描，**锁住的行集合大面积重叠**，极易互相阻塞并形成环。

### 场景 4：SELECT ... FOR UPDATE 范围条件 + 并发插入

RR 下 `FOR UPDATE` 对范围加 Next-Key Lock，不同事务以不同顺序锁定区间、再向区间内插入，间隙锁与插入意向锁冲突，可能成环。

### 场景 5：外键检查

插入/更新带外键的子表时，InnoDB 会对父表记录加锁。父表关联列若缺索引，会放大锁定范围，引入意料之外的等待与死锁。

## 六、造成的影响

### 6.1 锁超时的影响

1. **连接被占满**：等待线程被挂起却不释放连接，高并发下连接池迅速耗尽，应用表现为大面积请求超时。
2. **连锁阻塞 / 雪崩**：锁等待链越来越长，数据库 TPS 骤降；持锁方若也是慢 SQL，形成"慢 SQL → 锁等待 → 更多慢 SQL"的正反馈。
3. **数据一致性风险**：1205 只回滚单条语句，业务若未正确处理，可能出现"前半段已改、后半段失败"的部分成功状态。
4. **用户侧延迟与报错**：请求长时间 hang 住后失败，重试又进一步加大压力。
5. **主从延迟放大**：大事务在从库串行重放，持锁久会加剧主从延迟。

### 6.2 死锁的影响

1. **事务被回滚**：牺牲者事务的全部修改撤销，业务这一次操作失败。
2. **高死锁率 = 吞吐下降**：大量事务反复执行又反复被回滚，DB 做了无用功，系统有效吞吐降低。
3. **检测开销**：热点行高并发下，死锁检测 O(n²) 本身消耗 CPU。
4. **若无重试逻辑，直接转化为用户报错**；若有重试但退避不当，可能加剧争抢。
5. **业务数据看似"偶发丢失操作"**：实际是事务被回滚但未被监控发现。

> 注意：**偶发死锁是正常现象**，InnoDB 本就设计为通过回滚 + 重试来处理；需要警惕和治理的是**高频死锁**与**长时间锁等待**。

## 七、如何避免锁超时

核心思路：**让锁持有时间尽量短、锁定范围尽量小、等待能快速失败。**

### 7.1 缩短事务

- 事务里**只放必要的数据库操作**，绝不混入 RPC/HTTP 调用、消息发送、文件 IO、人工输入。
- 把慢查询、批量处理移到事务外；先准备好数据，最后开启事务快速提交。
- 及时 `COMMIT/ROLLBACK`，异常路径确保回滚（`try/finally`）。

### 7.2 缩小锁定范围

- 更新/删除条件**必须走索引**，并核对执行计划确实用到了索引。
- 用主键/唯一键精确定位，避免 `WHERE` 上对列做函数运算、隐式类型转换导致索引失效。
- 大批量更新拆成小批次（如每次按主键区间更新几百行），减少单次持锁行数与时间。

### 7.3 治理热点

- 热点行（库存、计数）拆分：单行计数改为多行/分桶求和，或用 Redis 预扣减后异步落库。
- 降低热点并发：排队、串行化、限流。
- 秒杀场景把"行锁竞争"前移到缓存层。

### 7.4 合理设置超时与监控

- 将 `innodb_lock_wait_timeout` 调整到与业务匹配的值（常见 5~10s），让异常快速暴露。
- DDL 设置 `lock_wait_timeout`，避免 MDL 长等。
- 监控状态指标并设置告警：

  ```sql
  SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_waits';     -- 锁等待次数
  SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time_avg';  -- 平均等待时长
  ```

### 7.5 安全执行 DDL

- 避开业务高峰期做 DDL；先用 `lock_wait_timeout` 限时。
- 使用在线 DDL 工具（`pt-online-schema-change`、`gh-ost`）或云厂商在线变更，避免 MDL 写锁长期阻塞。

## 八、如何避免死锁

死锁四个必要条件中，唯一能从设计上直接打破的是**循环等待**——办法就是**让所有事务按相同顺序加锁**。

### 8.1 统一加锁顺序（最有效）

- 全局约定：多表操作按固定表顺序；同表多行操作按主键**升序**加锁。
- 转账场景：不论谁转给谁，都先 `ORDER BY 账户ID` 锁定两个账户，再更新。

  ```sql
  START TRANSACTION;
  SELECT * FROM account WHERE acct_id IN (1,2) ORDER BY acct_id FOR UPDATE;
  -- 再执行扣款/入账
  COMMIT;
  ```

- 代码中批量更新前，先对待更新的 ID 排序，保证并发事务加锁顺序一致。

### 8.2 事务短小精悍

- 事务越短，持锁时间越短，相遇成环的窗口越小（同 7.1）。

### 8.3 让语句精确走索引

- 完善索引，避免行锁升级为大范围锁定，减少不同事务锁集合的重叠（同 7.2）。
- 外键关联列务必建索引。

### 8.4 谨慎使用范围锁定与高隔离级别

- 能用唯一键/等值定位就少用大范围 `FOR UPDATE`。
- 在业务允许时使用 **READ COMMITTED**：RC 下基本没有间隙锁，可显著减少间隙锁死锁（代价是接受不可重复读，需评估）。
- RR 业务中注意范围条件锁住的区间，缩小 `FOR UPDATE` 范围。

### 8.5 处理唯一键并发插入

- 业务侧尽量避免"先查后插"的竞态，直接使用 `INSERT ... ON DUPLICATE KEY UPDATE` / `INSERT IGNORE`。
- 批量插入的数据先排序、去重，降低同间隙并发。
- 对必然冲突的高并发插入做串行化或分片。

### 8.6 应用层重试

- 捕获 **1213/40001**，**重试整个事务**，并加**指数退避 + 随机抖动 + 次数上限**，避免同步重试再次相撞。
- 对 1205 也要有明确策略：重试或回滚，并记录日志与监控。

```text
伪代码：
for i in 1..N:
    try:
        begin; do business; commit;
        return
    catch Deadlock(1213) / LockTimeout(1205):
        rollback()
        sleep((2^i + random) * base)   // 指数退避 + 抖动
give up and alarm
```

## 九、生产应急处理流程

当数据库出现大量锁等待/死锁告警时：

1. **定位等待链**：用 [05-transaction.sql](./05-transaction.sql) 第七节的查询，找出 `blocking_thread`（持锁最久的源头事务）及其 SQL。
2. **判断源头**：看 `INNODB_TRX.trx_started` 与 `trx_query`，确认是长事务、慢 SQL，还是忘记提交的连接。
3. **快速止血**：必要时 `KILL <blocking_thread>` 终止源头事务，释放其锁；连锁等待会随之解除。
4. **看死锁日志**：`SHOW ENGINE INNODB STATUS` 分析两边的加锁顺序，定位是哪段代码。
5. **事后治理**：补索引、缩短事务、统一加锁顺序、完善 1213/1205 重试与监控告警。

> 8.0+ 可通过 `performance_schema.data_locks` / `data_lock_waits` 看到更细的锁模式与记录；5.7 使用 `information_schema.INNODB_LOCK_WAITS`（配合 `INNODB_TRX`）。

## 十一、应用层最佳实践清单

- [ ] 事务短小，不夹任何外部 IO 与人工操作，异常路径必回滚。
- [ ] 所有更新/删除条件走索引，上线前用 EXPLAIN 核对。
- [ ] 多表/多行更新统一加锁顺序（按主键升序）。
- [ ] 热点行拆分或前移到缓存，避免单行高并发竞争。
- [ ] 大事务拆小批量，低峰期执行 DDL，优先在线 DDL。
- [ ] 捕获 1213：指数退避重试**整个事务**；捕获 1205：明确重试或回滚。
- [ ] 合理配置 `innodb_lock_wait_timeout`（建议 5~10s）与 `lock_wait_timeout`。
- [ ] 监控 `Innodb_deadlocks`、`Innodb_row_lock_waits`、平均等待时长并告警。
- [ ] 业务允许时评估使用 RC，减少间隙锁死锁。
- [ ] 唯一键写入使用 `ON DUPLICATE KEY UPDATE`，避免"先查后插"竞态。
